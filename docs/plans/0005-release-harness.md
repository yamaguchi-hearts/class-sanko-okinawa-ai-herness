# 0005: リリース・ハーネスと品質ゲートPlan

## 目的

本Planは、要件の整理からWindows配布後の確認までを、担当者や実行環境が替わっても追跡・再実行できる工程へそろえる。ここでいうハーネスは、リポジトリに固定する実行コマンド、品質ゲート、検証証跡、設計・実装の引き継ぎ規約の組である。外部CI、配布サービス、自動更新機能を導入すること自体は本Planの前提にしない。

対象アプリの機能要件は [0003](0003-store-inventory.md)、DEMO向け差分とpnpm/lint導入は [0004](0004-demo-enhancements.md) を定義元とする。本Planはそれらを置き換えず、リリースまでに確認する順序と完了条件を定める。

## 現状評価

| 観点 | 評価 | 根拠・不足 |
| --- | --- | --- |
| 機能・権限・データ保護 | 計画済み | 0003と要件別設計に、認証、監査、バックアップ、復元、Windows配布を定義済み。Phase 4/5には未検証項目が残る。 |
| DEMO差分 | 実装済み・一部検証待ち | 0004のパスワード、初期在庫、画像を実装し、型検査・単体テスト・ビルド・E2E一部を実行済み。Windows配布と画像操作の実機検証が残る。 |
| パッケージ管理の再現性 | 実装済み | `pnpm@12.14.0`、`pnpm-lock.yaml`、`pnpm-workspace.yaml`、pnpm scriptsへ移行済み。クリーン環境でのfrozen導入をリリースゲートとして確認する。 |
| 静的解析 | 実装・検証済み | ESLint設定と`lint`/`check`を追加し、typescript-eslintの対応範囲に合わせてTypeScript 6.0.3へ固定する。 |
| リリース判断 | 要整備 | テストと配布の記述はあるが、候補作成から公開・差戻しまでの共通ゲート、証跡、承認者が一か所に定義されていない。 |
| 署名・配布・更新方針 | 未確定 | 証明書、配布先、更新配布の有無、保持期間は管理者判断が必要であり、推測で確定しない。 |

pnpm移行とlintの互換性対応を完了したため、本PlanのG2以降は型検査・テスト・ビルド・E2E・配布検証の結果に基づいて判定する。

## 標準工程と品質ゲート

| 段階 | 自動化するハーネス | 人が確認・承認すること | 出力・通過条件 |
| --- | --- | --- | --- |
| G0: 要件固定 | Plan/設計/プロンプトの要求ID対応、未確定事項の列挙 | 範囲、互換性を壊す変更、未確定事項の決定 | 対象要求、受入条件、実装順、判断待ちが追跡可能。重要な未決定を確定扱いしない。 |
| G1: 再現可能な準備 | `pnpm install --frozen-lockfile`、lockfile差分確認、依存ビルド許可の確認 | Node/pnpm固定値と依存更新の妥当性 | クリーン環境で導入でき、不要なlockfileや未固定ツールに依存しない。 |
| G2: 変更の品質 | `pnpm run lint` → `pnpm run typecheck` → `pnpm run test` → `pnpm run build` → `pnpm run test:e2e` | 失敗・skip・環境制約の切り分け、例外の承認 | 全必須コマンドが成功。`lint`は警告も失敗とし、広域ignore/disableでの回避を認めない。 |
| G3: 配布候補 | `pnpm run dist:win`、`pnpm run dist:recovery`、`pnpm run test:packaged` | 新規導入、更新導入、復元、復旧exe、Windows実機の結果を確認 | 候補生成物、対象コミット、バージョン、ハッシュ、実行結果を対応付ける。既存DBを失わず、移行は一度だけ適用される。 |
| G4: 公開判断 | 生成物ハッシュとリリースノートの照合 | 署名、配布先、対象者、既知の制約、ロールバック可否を管理者が承認 | 承認記録、配布先、公開版、復旧手順を残す。未承認なら候補のままとする。 |
| G5: 公開後確認 | 配布物からの起動・基本業務確認、問題記録 | 問題時の配布停止、前版への差戻し、利用者連絡 | 公開結果、既知問題、次回への改善項目を記録する。 |

G2の短縮入口は、0004で定義する`pnpm run check`（lint→typecheck→単体/DBテスト）とする。ただし`check`の成功だけではE2E、パッケージ版、Windows実機、更新導入を通過したことにはならない。

## リリース候補の証跡

リリース候補ごとに、既存の検証記録または専用のリリース記録へ次を残す。値を得られない欄は空欄にせず「未実行」と理由を記載する。

- 対象バージョン、GitコミットID、作業ツリーがクリーンだったか、Node/pnpm版、`pnpm-lock.yaml`の識別値。
- 各品質ゲートの実行日時、Windows版、コマンド、成否、失敗・skipの理由、ログの保存先。
- NSISと復旧exeのファイル名、SHA-256、生成元コミット、署名状態、配布先。
- 新規導入・更新導入で使用した分離済みuserData、DBスキーマの開始/終了版、移行・復元・復旧の結果。実ユーザーDBや認証情報は証跡に含めない。
- リリースノート（利用者に影響する変更、DB移行、既知の制約、必要なバックアップ/復旧案内）と管理者の公開可否。

生成物とログの置き場所・保持期間は配布先の決定と合わせて決める。リポジトリへバイナリ、実DB、秘密情報、認証情報をコミットしない。

## リリースを止める条件と差戻し

次のいずれかがある候補は公開しない。例外公開が必要なら、影響・代替策・期限を記録して管理者が明示承認する。

- pnpmのfrozen導入、lint、型検査、必須テスト、ビルド、配布候補確認の失敗または未実行。
- 既存DBの移行、更新導入、バックアップ/復元、復旧exeにデータ喪失・認証回避・権限逸脱の懸念がある。
- 生成物と対象コミット/lockfile/バージョンの対応を説明できない、またはハッシュ・署名状態を確認できない。
- 高重要度の既知不具合、秘密情報の混入、依存ビルドの黙ったスキップ、未承認の互換性破壊がある。

公開後に上記が判明した場合は、まず配布を停止して対象版・影響範囲・利用者のDB操作状況を記録する。前版への差戻しは、DBスキーマが前版と互換か、復元を要するかを確認してから案内する。アプリを単に上書きしてDBを破損させない。必要時は既存のバックアップ/復元・管理者復旧手順を使い、事後に原因、対処、再発防止を記録する。

## 管理者決定が必要な項目

以下は技術担当・エージェントが推測で確定せず、G4より前に管理者が決める。

1. Windowsコード署名証明書の有無、保管責任者、署名を必須にする初回リリースの時期。
2. 配布先（社内共有、手動配布、将来の更新配布）、対象利用者、生成物・ログの保管場所と保持期間。
3. バージョン付与、Git tag、リリースノートの承認者、公開可否の最終責任者。
4. 対象Windows版、検証端末、Excel表示確認の対象版、更新導入の最低サポート範囲。
5. 重大障害時の連絡先、配布停止の権限、復元判断の責任者。

これらが未決定でもG0〜G3の候補作成・技術検証は進められるが、署名・配布先・責任者が未確定の候補は公開しない。

## 適用順

1. 0004のpnpm移行とESLint導入を実装し、R-PNPM/R-LINTとG1/G2の前提を満たす。
2. 0004のDEMO差分を実装し、機能別の受入条件と統合検証を満たす。
3. 0003で未完了のPhase 4/5検証を、pnpm/lint導入後の標準コマンドで再実施し、過去記録と区別して残す。
4. 本PlanのG3でWindows配布候補を作成し、G4の管理者決定・承認後にだけ公開する。
5. 公開後の結果をG5へ記録し、次のPlanや設計判断へフィードバックする。

このPlanは工程を定める文書であり、pnpm、ESLint、CI、署名、配布物をこの文書だけで実装済みにはしない。各実装・検証の完了は、対応する設計、コミット、検証記録で更新する。
