## 現状と移行

調査時はPhase 3までコミット済みで、Phase 4の保守・復旧・移行5やREADME等に未コミット変更がある。それらの実装状態を確認してから変更を重ね、他の作業を無断で取り込まない。今回の設計コミットは新規文書だけとする。

新規移行はOPENING部分一意索引とproduct_imagesが対象。調査時の次番号は6以降だが予約はせず、実装開始時の最新適用番号に続ける。既適用1〜5を変更しない。画像なしの旧DBを移行し、既存の在庫・履歴・ユーザー・設定を保持する。

バックアップ検査、復旧ツール、再起動マーカー回復のスキーマ上限を同時更新する。単にDB接続側だけ対応版を増やすと、新しく作ったバックアップが復元できなくなる。Phase 4の現在の `src/main/services/maintenance.ts` には5を上限とする判定があるため必ず確認する。

## 設計判断

管理者が確定したのはpnpm、linter、画像、初期在庫とDEMO4文字下限。以下は設計側の具体化である。

- ESLint flat config + TypeScript/React Hooksルール。formatterの一括導入は対象外。
- 画像は任意1枚、PNG/JPEG入力、5MiB/各辺4,096、PNGへ正規化、SQLite BLOB。
- 画像候補はMainの短命・本人限定選択ID。商品保存と同時に確定する。
- 初期在庫は商品作成専用、正数のみOPENING、0は履歴を作らない。理由OTHERと固定メモで既存enumを維持する。
- パスワードの本番/DEMO切替は追加せず、今回のDEMOポリシーを共通化する。

## 統合受け入れゲート

1. 固定pnpmのfrozen-lockfile導入→lint→型検査→単体/DB→ビルド→Electron E2Eを再現する。
2. 4文字ADMINセットアップ→画像と初期在庫付き商品登録→STAFF参照/通常在庫操作→画像変更と初期在庫編集の拒否。
3. 再起動後に画像・在庫・OPENING履歴が残り、セッションだけ失効する。
4. 画像を含むバックアップ→商品/在庫/画像変更→復元→再起動でスナップショットが戻る。旧版DBも移行可能。
5. NSIS版・復旧exeがpnpm由来の依存構成で動き、SQLite/Argon2idを利用できる。
6. 更新インストールで既存DBを保持し、新規移行を一度だけ適用する。
