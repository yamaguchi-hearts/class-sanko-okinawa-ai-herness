# 設定・バックアップ・復元

[設計索引](../README.md) / 対応: 原Plan §3.7、§6.7、§10 Phase 4

## 設定 F-SETTINGS

ADMINのみ設定を参照・更新できる。店舗名はtrim後1〜100文字、無操作ロック時間は整数1〜60分・既定15分とする。ロック無効化の設定は設けない。日時はOSローカル表示で固定し、初期版で不要な表示形式編集を増やさない。

DB保存先は読取専用で設定画面とREADMEへ示す。RendererからDBパスを書き換える機能は設けない。設定更新と監査を同一トランザクションで保存し、ロック時間を短縮した場合はMainの現在の最終操作時刻から直ちに再評価する。

## 手動バックアップ F-BACKUP

ADMINがMainの保存ダイアログで選ぶ。出力形式はアプリ識別・スキーマ・設定を含む一貫したSQLiteファイル（.sqlite3）とする。backup APIを使うか接続を閉じて整合性を確保し、使用中DBの単純コピーはしない。WAL等のサイドカーを取り残す方式を禁止する。

候補出力を一時ファイルで完成させ、整合性検査後に保存する。バックアップ識別子、作成日時、スキーマ、結果を監査する。実行中も認証境界を保ち、完了前にロックした場合は結果をロック画面へ露出しない。

説明には手動で別媒体へ定期保存すること、暗号化なし・PCローカル管理者の限界・バックアップにユーザー情報も含まれることを示す。自動クラウド転送は行わない。

## 検証付き復元 F-RESTORE

通常アプリ内はADMINのみ。Mainで開くダイアログを出し、元DBそのものではなく隔離領域へコピーした候補を検査する。

検査内容はSQLite形式、アプリ識別、対応するschema_migrations、必要テーブル/カラム、integrity_check、foreign_key_check、在庫不変条件、セットアップ済み状態、有効ADMINの存在。未来版・別アプリ・壊れたDB・必要データ欠落を `BACKUP_INVALID` として適用前に拒否する。対応する旧版は候補コピーを移行して再検査する。

### 適用手順

1. 候補、店舗、作成情報、置換の影響を確認画面へ表示する。Main内選択IDに結びつけ、パスの任意指定を禁止する。
2. 確認後にADMIN認可と候補同一性を再確認する。新規業務処理を止め、実行中の処理が終わるまで待つ。
3. 現DBの自動事前バックアップを作る。作成・検証できなければ復元を開始しない。
4. 全接続を閉じてサイドカーを整理し、現DBを別名退避する。復元中マーカーに原本・候補・段階・チェック情報を記録し、秘密は入れない。
5. 検証済み候補をuserDataと同一ボリュームの作業領域から入れ替える。再接続・整合性検査し、古い再設定コードをすべて失効させる。
6. 復元後DBへ `BACKUP_RESTORED` を記録する。元の実行者が存在しなければFKはnullとし、スナップショットを用いる。
7. DBと監査が確定したら全セッションを破棄し、ユーザーに再起動を要求する。再起動後は復元したDBの認証情報でログインする。古いセッションを復元しない。

失敗時は入替候補を停止して退避DBと対応するサイドカーを一貫した状態へ戻し、再接続・検査後に元のデータで再開する。安全な再開ができなければ通常画面へ戻さず保守エラーと退避場所を示す。復元の成功と監査失敗を別々に無視しない。

プロセス強制終了や停電後の起動では、通常のマイグレーションより先に復元中マーカーを処理する。完了が検証できない場合は保管済み原本へ戻す。Windowsで開いたファイルの置換に依存せず、候補・原本・マーカーの状態ごとの復旧を統合テストする。

オフライン復旧ツールはこの検査・退避・適用・復帰のサービスを再利用する。認可だけをWindows管理者権限と明示確認に置き換える。

## 受け入れ条件

F-SETTINGS-01: STAFFの読取/変更を拒否し、範囲外設定を拒否し、15分既定と時間短縮時の再評価が機能する。

F-BACKUP-01: 書込み中でも一貫したファイルを作れ、復元テストで在庫・履歴・ユーザーが一致する。

F-RESTORE-01: 不正/未来/別アプリ/整合性不良を現DBに触れず拒否する。

F-RESTORE-02: 事前バックアップ、候補入替、再接続、監査の各失敗と強制終了を注入し、原本が回復できる。成功後も旧セッション・再設定コードは使えない。
