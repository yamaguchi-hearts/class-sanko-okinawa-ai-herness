# セキュリティとデータ保護

[設計索引](../README.md) / 対応: 原Plan §3.1、§5、§12

## 要求 R-SEC

- 認証・認可・パスワード・セッション・DB・ファイル操作はMainが管理する。Rendererのロール表示や入力検証だけで許可しない。
- BrowserWindowは `contextIsolation: true`、`nodeIntegration: false`、sandboxを有効にできる構成とする。Preloadは限定したcontextBridge APIのみ公開する。
- Mainは許可したトップレベルフレーム、webContents、アプリURLを照合する。子フレームや別ウィンドウ・外部ページからのIPCを拒否する。
- ナビゲーションと新規ウィンドウは既定拒否。外部コンテンツを業務ウィンドウに読み込まない。
- 本番CSPに不要な `unsafe-eval` 等を含めず、DevToolsの自動起動や開発用バックドアを出荷しない。
- セッションはMainメモリとPreload内の非公開状態だけで扱い、RendererのlocalStorage/sessionStorage、DB、ログへ保存しない。Rendererへ返すSessionViewは秘密トークンを含まない。
- パスワードはArgon2idの専用ライブラリでソルト付きハッシュを保存する。パラメータ・採用理由・Windowsでの処理時間はPhase 0で記録する。平文、復号可能保存、固定ソルト、独自パスワードハッシュを禁止する。
- ログ、監査、例外、テスト出力にパスワード、ハッシュ、認証・再設定コード、セッショントークン、DB接続詳細を出さない。
- SQLパラメータをバインドし、ソート等の識別子は許可リストから選ぶ。

## セッションと制限

発行先webContentsと短命なセッションを結びつけ、保護APIごとに有効期限、ロック、アカウント有効性、現在のロールを再検証する。ロール変更・無効化・パスワード変更・再設定要求は既存セッションを失効させる。ロック時は業務トークンを破棄し、Mainのロック文脈に本人の識別子だけを保持する。

連続認証失敗とクールダウンをDBへ保存する。未知のログインID、誤パスワード、無効アカウントは同じ公開エラーとし、存在確認専用の情報を返さない。未知IDも共通の制御で連打を抑える。詳細は認証設計に従う。

## ローカルPCでの限界

DB暗号化は初期版の必須ではない。SQLite内の商品・在庫は平文であり、パスワードハッシュはDB全体を暗号化しない。Windows管理者やDBファイルへ直接アクセス可能な人に対する完全な改ざん耐性は保証しない。バックアップにも同じ制約がある。READMEとバックアップ説明に明記する。

管理者復旧ツールはこのローカル管理権限を使う明示的な保守手段とし、通常アプリ内の秘密の回避口にはしない。

## 受け入れ条件

R-SEC-01: 未認証、期限切れ、他webContents、子フレーム、権限不足、無効ユーザーをMainで拒否するテストがある。

R-SEC-02: パッケージ版でNode APIがRendererから利用できず、任意チャンネル送信・外部遷移を許可しない。

R-SEC-03: DBとログに平文パスワード・トークン・再設定コードがなく、DB非暗号化と復旧ツールの権限境界が運用文書に記載される。
